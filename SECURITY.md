# Security Policy

## What ghorg can do

ghorg clones every repository an organization or user exposes to the token
you give it, and updates the clones it already has. It runs **as you**, with
that token's reach.

- **Tokens** come from the provider's `GHORG_*_TOKEN` variable, `--token`, or
  the config file; each accepts the token itself or a path to a file holding
  it. Without one, ghorg falls back to `gh auth token` for GitHub and, on
  macOS, to the login Keychain for GitHub, GitLab and Bitbucket. A GitHub App
  key (PEM path) is read from disk and never copied. Prefer a file or the
  environment to `--token`, which other local users can see in the process
  list. `GHORG_NO_TOKEN=true` clones anonymously.
- **Credentials and clones.** ghorg clones with the token embedded in the
  URL and immediately rewrites `origin` to the bare URL, restoring the
  credential only for the duration of an operation that needs it (fetch-all,
  sync) and stripping it again afterwards. A clone left with a token in
  `.git/config` is a bug — see the scope list below.
- **Pull, clean and sync change your working trees.** By default an existing
  clone is pulled and `git clean`ed; `--no-clean` and `--protect-local` turn
  that down. `--sync-default-branch` merges upstream into the default branch
  with safety checks, but it still writes to repositories you may be working
  in. Point ghorg at a directory it owns.
- **TLS** is verified against the system roots. The
  `--insecure-{gitlab,gitea,bitbucket,sourcehut}-client` flags turn
  verification off or permit plain HTTP for that provider: anyone on the
  network path can then read the token. Use them only for an instance you
  can reach no other way.
- **`ghorg reclone-server`** listens on every interface
  (`GHORG_RECLONE_SERVER_PORT`) with **no authentication**: any caller can
  start a reclone of any entry in your `reclone.yaml`, which runs with your
  tokens, and, with `GHORG_STATS_ENABLED=true`, read the stats file. **The
  network is the boundary**: expose it only on a private network, or bind it
  behind a proxy that authenticates.
- **The container image** runs as an unprivileged `ghorg` user (uid 1111),
  writes clones to `/data` and reads its config from `/config`. Pass tokens
  as environment variables or mounted files, never baked into a derived
  image.

## Supported versions

ghorg is pre-stable (`v0.x`). Only the latest release receives fixes.

## Verifying a release

Releases from v0.1.6 on are signed with
[cosign](https://github.com/sigstore/cosign) keyless signing: the signature is
tied to the GitHub Actions workflow that built the release, not to a key
someone could leak. `.github/workflows/release.yml` runs the shared workflow
in [blairham/.github](https://github.com/blairham/.github)
(`.github/workflows/go-release.yml`), so the signing identity is that shared
workflow; the certificate also names this repository and the tag.

**Downloads.** `checksums.txt` is signed; it lists the digest of every
archive. Verify the signature, then the archives against it:

```sh
VERSION=v0.1.6
cosign verify-blob \
  --certificate-identity-regexp '^https://github\.com/blairham/\.github/\.github/workflows/go-release\.yml@' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-github-workflow-repository blairham/ghorg \
  --certificate-github-workflow-ref "refs/tags/$VERSION" \
  --bundle checksums.txt.sigstore.json checksums.txt
sha256sum --check --ignore-missing checksums.txt
```

**Provenance.** Every archive carries SLSA build provenance, generated by
[`actions/attest-build-provenance`](https://github.com/actions/attest-build-provenance)
in the release workflow and stored in the repository's attestations:

```sh
gh attestation verify "ghorg_${VERSION#v}_Linux_x86_64.tar.gz" --repo blairham/ghorg \
  --signer-workflow blairham/.github/.github/workflows/go-release.yml
```

The same bundle is attached to the release as `ghorg-$VERSION.intoto.jsonl`,
for checking offline:

```sh
gh attestation verify "ghorg_${VERSION#v}_Linux_x86_64.tar.gz" --repo blairham/ghorg \
  --bundle "ghorg-$VERSION.intoto.jsonl" \
  --signer-workflow blairham/.github/.github/workflows/go-release.yml
```

**Image.** `ghcr.io/blairham/ghorg` is signed by digest (image tags carry the
`v`):

```sh
cosign verify "ghcr.io/blairham/ghorg:$VERSION" \
  --certificate-identity-regexp '^https://github\.com/blairham/\.github/\.github/workflows/go-release\.yml@' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-github-workflow-repository blairham/ghorg
```

and carries SLSA build provenance, stored in ghcr.io beside it and in the
repository's attestations. The subject is the multi-arch index, so check it
by tag:

```sh
gh attestation verify "oci://ghcr.io/blairham/ghorg:$VERSION" --repo blairham/ghorg \
  --signer-workflow blairham/.github/.github/workflows/go-release.yml
```

Releases up to and including v0.1.5 are unsigned and carry no provenance.

## Reporting a vulnerability

**Do not open a public issue.** Report it privately through GitHub:
[Security → Report a vulnerability](https://github.com/blairham/ghorg/security/advisories/new).

Please include the affected version or commit, what an attacker can do, and
the steps to reproduce. You should receive a response within a week.

In scope, among others:

- a token, app password or private key written to a log, the state manifest
  (`_ghorg_state.json`), the stats CSV, or a clone's `.git/config`
- a TLS connection that skips verification, or a token sent over plain HTTP,
  without the matching `--insecure-*-client` flag
- a repository name or path from a provider that makes ghorg write outside
  the clone directory
- `reclone-server` running anything other than `ghorg reclone` for an entry
  in the configured `reclone.yaml`

Out of scope: anything that follows from exposing `reclone-server` to a
network you do not trust, or from running with an `--insecure-*-client` flag.
